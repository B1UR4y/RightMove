## 1. О ПРОЕКТЕ

Система компьютерного зрения для оценки техники физических упражнений по видео с одной камеры. Пользователь выбирает упражнение, выполняет его перед камерой, получает: подсчёт повторений, подсказки об ошибках (текст + голос), отчёт с графиком ошибок и оценкой тренировки.

Первая версия — веб/десктопный прототип. Целевые упражнения MVP: приседания, отжимания, подтягивания, скручивания, jumping jacks.

## 3. КРИТИЧЕСКИЕ ПРАВИЛА (не нарушать)

Правило 1. Порядок импортов в скриптах.
Сначала `from ultralytics import YOLO` — PyTorch загружает свои встроенные DLL из torch/lib. НЕЛЬЗЯ добавлять системные пути CUDA/cuDNN в PATH до этого импорта, иначе WinError 127.
Потом `setup_cuda_paths()` (добавляет CUDA_BIN и CUDNN_BIN в PATH и os.add_dll_directory).
Потом `import onnxruntime` и `ort.preload_dlls(cuda=True, cudnn=True)` — для RTMPose.

Правило 2. Пути к CUDA/cuDNN.
CUDA_BIN = r"C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v13.2\bin"
CUDNN_BIN = r"C:\Program Files\NVIDIA\CUDNN\v9.26\bin\13.4\x64"

Правило 3. Копирование кадров перед рисованием.
При прогоне нескольких моделей на одних и тех же кадрах всегда `frame = src.copy()` перед `draw_skeleton`. Иначе скелеты накапливаются на одном массиве и получаются "пучки".

Правило 4. Кодек видео.
avc1 (H.264) — предпочтительно. Fallback на XVID, потом mp4v. Для avc1 нужен openh264-2.5.0-win64.dll рядом со скриптом или в PATH.

Правило 5. Приведение к float при расчёте bbox.
`bw_f, bh_f = float(bw), float(bh)`, затем `diag = sqrt(bw_f**2 + bh_f**2)`. Иначе при bbox типа uint16 происходит overflow, и PCK занижается.

Правило 6. Выбор человека при нескольких детекциях.
Функция `pick_best_person()` выбирает детекцию с наибольшей площадью bbox среди точек с confidence > 0.3. НЕ используйте `[0]` — это частая причина ложных детекций.

Правило 7. 3D-модели не рассматривать.
У пользователей одна камера. Никакие 3D-модели и multi-view не подходят.

## 9. СЛЕДУЮЩАЯ ЗАДАЧА: ПОДСЧЁТ ПОВТОРЕНИЙ

Формализация повторения: завершённый цикл движения (например, для приседа — переход из стоя в нижнюю точку и обратно). Считать нужно события завершения, а не кадры.

Основные сигналы по упражнениям:
- Приседания: угол бедро-колено-лодыжка; вертикаль таза
- Отжимания: угол плечо-локоть-запястье; линия плечо-таз-лодыжка
- Подтягивания: угол плечо-локоть-запястье; положение запястий относительно головы
- Скручивания: угол корпуса (плечо-таз) к вертикали
- Jumping jacks: расстояние между стопами и запястьями

Варианты реализации:

Вариант A. Конечный автомат (FSM) + пороги + гистерезис. РЕКОМЕНДУЕТСЯ ДЛЯ MVP.
Состояния: стоя / опускание / низ / подъём. Два порога с гистерезисом (вход и выход из фазы). Проверка минимальной амплитуды (разница углов между верхом и низом). Проверка минимальной/максимальной длительности. Блокировка повторного счёта. Плюсы: простой, быстрый, объяснимый, не требует разметки. Минусы: пороги под упражнение и ракурс, чувствительность к шуму.

Вариант B. Детекция пиков через scipy.signal.find_peaks.
Параметры: prominence, distance, width. Хорошо для периодических движений (приседания, jumping jacks). Для realtime нужен lookahead или каузальная версия. Хуже для асимметричных фаз (подтягивания).

Вариант C. Анализ производной.
Смена знака производной = смена фазы. Устойчивее к дрейфам, но усиливает шум. Обычно как дополнение к A.

Вариант D. DTW с эталонной траекторией.
Устойчиво к разному темпу, но нужны эталоны, дороже по вычислениям. Для офлайн-анализа или целевой системы.

Вариант E. ML на последовательностях (TCN/LSTM/1D-CNN).
Признаки — нормализованные координаты и углы за окно 30–60 кадров. Плюсы: устойчивее. Минусы: нужна разметка повторений, менее объяснимо. Не для MVP.

Вариант F. Гибрид: FSM + ML-подтверждение.
Для целевой системы.

Вариант G. Ultralytics AIGym.
Готовый класс solutions.AIGym(model, kpts=[6,8,10], up_angle=145, down_angle=90). Простой счётчик по углу между тремя точками с встроенным трекингом. Ограничения: нет минимальной амплитуды, нет гистерезиса, одна пара порогов, нет асимметрии. Годится как baseline и референс, не как финальное решение.

Обязательная предобработка сигналов:
- Сглаживание (EMA или Savitzky-Golay) — углы дрожат от кадра к кадру
- Фильтрация по confidence (порог ~0.3–0.5)
- "Замораживание" состояния при пропаже ключевой точки
- Интерполяция коротких пропусков (1–3 кадра)
- Нормировка расстояний на длину торса/бедра
- Выбор стороны (левая/правая), не удваивать счёт
- Калибровка порогов под упражнение в конфиге

## 10. РЕКОМЕНДУЕМАЯ АРХИТЕКТУРА

Разделение ответственности: счётчик повторений и анализатор техники — независимые модули с единым источником данных.

Источник данных: один поток от YOLOv8n в формате `{frame_idx, timestamp, kpts_13 (x, y, confidence), person_bbox}`.

Счётчик повторений:
- FSM на одном основном сигнале с гистерезисом, минимальной амплитудой, минимальной/максимальной длительностью.
- Эмитит `RepEvent {rep_id, start_frame, end_frame, primary_signal_min, primary_signal_max, duration_ms, valid}` в момент завершения повторения.

Анализатор техники:
- Движок правил (rule engine), два слоя.
- Покадровый слой — ошибки, не зависящие от границ повторения (вальгус, наклон корпуса, разведение локтей, асимметрия). Эмитит `FrameError {frame_idx, error_type, body_part, confidence}`.
- Слой по повторению — ошибки, требующие буфера кадров повторения (глубина, темп, consistency, пауза). Подписывается на RepEvent, эмитит `RepErrors {rep_id, errors[], severity}`.

Обратная связь:
- Покадровые ошибки — сразу (popup + голос + подсветка сустава).
- Отложенные — по завершении повторения.
- Cooldown на повторные ошибки (не чаще раза в 2–3 секунды), дедупликация в пределах повторения.

Один поток точек от YOLOv8n для обеих задач. Halpe-26/ML — только для офлайн-анализа загруженного видео или целевой системы.

Хранение по повторению (для отчёта ФТ-12/13/18-21): номер, длительность, амплитуда, уверенность, флаг валидности, список ошибок, кадры с ошибками.

## 11. КОНТРАКТ МЕЖДУ МОДУЛЯМИ

Вход счётчика и анализатора (общий поток):
- frame_idx: int
- timestamp: float

Выход анализатора: FrameError, RepErrors

## 12. ПОДВОДНЫЕ КАМНИ

- Рассинхронизация событий: единый буфер кадров и единое сглаживание.
- Частичные повторения: счётчик решает, засчитывать ли; анализатор не должен ругаться на "недостаточную глубину" непризнанного повторения.
- Пропуски точек: "замораживать" оба модуля, не выдавать ложные ошибки.
- Разные ракурсы: правила и пороги зависят от ракурса; конфиг упражнения включает рекомендуемый ракурс.
- Асимметрия: считать обе стороны, но не удваивать счётчик повторений.
- Утечка скелета в фон: pick_best_person по наибольшему bbox.
- MediaPipe отправляет телеметрию в Google: отключить через переменные окружения, если беспокоит.

## 14. ЧТО СДЕЛАТЬ В ПЕРВУЮ ОЧЕРЕДЬ В НОВОМ ЧАТЕ

## 16. КЛЮЧЕВЫЕ УРОКИ

- Новейшая модель не значит лучшая: YOLO26 проиграл YOLOv8n по всем ключевым метрикам на реальных данных фитнес-упражнений.
- Больше точек не значит точнее: Halpe-26 не дал существенного прироста над RTMPose-Body в 13 базовых точках.
- Скорость важна: 73 FPS против 27 FPS — критическая разница для realtime с отрисовкой, озвучкой и логикой.
- Проблема 1680 (все модели ~45% PCK) — это данные, а не модели. При интерпретации исключать из средних или анализировать отдельно.
- Разделение счётчика и анализатора техники — правильная архитектура, позволяет тестировать и развивать модули независимо.
